# Solana Framed-Transaction Arb Prediction
## Literature Review, Model Selection, and Training Strategy

**Date:** 28 September 2026  
**Purpose:** Select the model architecture and training protocol for predicting arbitrage creation from a framed Solana transaction using only information available before execution.

---

## 1. Executive conclusion

The recommended system is **not one monolithic model** and it is **not a large Transformer in the live path**.

The strongest architecture for this problem is:

```text
(program, instruction-family) historical prior
                    +
        rich framed-TX teacher model
                    ↓
       calibrated multi-task outputs
                    ↓
          knowledge distillation
                    ↓
 tiny family-conditioned production student
                    ↓
      sub-µs / low-µs live inference
```

### Recommended research/training stack

**Mandatory baselines**

1. Family-only empirical prior.
2. CatBoost / LightGBM / XGBoost on engineered structural transaction features.
3. Small MLP / DCN-V2-style interaction model.
4. TabM-style MLP ensemble as a strong neural tabular teacher baseline.
5. Rich hybrid teacher:
   - structural/tabular branch,
   - categorical identity embeddings,
   - small raw-instruction-byte encoder,
   - family prior as a logit offset,
   - multiple prediction heads.

### Recommended live model

Train the richest teacher that gives useful OOS information, then **distill it into a tiny family-conditioned student**.

The student should be benchmarked between:

- a very small MLP/DCN residual model,
- a compact oblivious-tree ensemble,
- or family-specialist variants selected by an O(1) trigger-family lookup.

The final choice should be made by **economic value per unit latency**, not by AUC alone.

### Main target

The core deployed target is:

\[
P(\text{executable arb created}\mid \text{framed transaction})
\]

with secondary heads for:

- expected / bucketed net opportunity value,
- top-K route or route-family distribution,
- hop depth,
- optional optimal-size hint,
- opportunity survivability.

Capture/competition prediction should be treated as a **separate, more frequently refreshed model**, because competition is less stationary than deterministic opportunity creation.

# 2. Formal problem

Let:

- \(S_t\) = exact pre-transaction Solana state,
- \(T_t\) = framed transaction,
- \(F\) = deterministic Solana execution function,
- \(S_{t+1}=F(S_t,T_t)\),
- \(A(S)\) = exact arb oracle over state \(S\).

Then the economic target is deterministic if both state and transaction are known:

\[
Y_t = A(F(S_t,T_t))
\]

or more specifically:

\[
Y_t =
\mathbf{1}
[
A(F(S_t,T_t)) - A(S_t) > \text{economic threshold}
]
\]

The live model intentionally does **not** observe the complete \(S_t\). It sees only transaction information \(X(T_t)\).

Therefore the statistical problem is:

\[
P(Y_t \mid X(T_t))
\]

This is an important distinction.

The target itself is not analogous to predicting tomorrow's FX price. The uncertainty seen by the model comes mainly from **hidden current state** and incomplete observability.

The model is learning which observable transaction structures imply particular hidden-state/state-transition outcomes often enough to justify sending.

---

# 3. Why this is different from conventional trading ML

Traditional financial prediction often targets something such as:

\[
P(r_{t+h}>0\mid X_t)
\]

where the future return is generated by a continuously evolving stochastic environment involving:

- new information,
- human behavior,
- macro events,
- liquidity changes,
- other agents,
- regime drift.

Our arb-creation target is closer to:

\[
P(g(S_t,T_t)>0 \mid T_t)
\]

where \(g\) is deterministic and the unknown quantity is largely \(S_t\).

This does **not** make the problem perfectly stationary.

Non-stationarity remains in:

- pool liquidity distributions,
- new markets,
- program upgrades,
- transaction composition,
- fee economics,
- token popularity,
- competitor behavior,
- route universe.

But the causal mechanism of a fixed program/instruction version is much more stable than a conventional future-return label.

A useful decomposition is:

### Structural / mechanical target

```text
Did the transaction create executable arb?
How much?
Which route?
What size?
```

This should be relatively stable while the program version and economic mechanism remain unchanged.

### Competition target

```text
Was the opportunity captured?
How quickly?
Did someone beat us?
How long did the edge survive?
```

This can change rapidly as competitors adapt.

The production system should therefore avoid combining both concepts into one opaque target.

---

# 4. Connection to partially observable systems

Predictive State Representation (PSR) literature studies systems where the underlying state is not directly observed and predictive representations are built using observable quantities.

The analogy is not exact—the proposed arb classifier is not itself a PSR—but it provides a useful conceptual frame:

- true blockchain state is latent to the hot-path classifier,
- the framed transaction is observable,
- historical data reveals relationships between observable transaction patterns and deterministic resulting outcomes.

PSR research shows that useful predictive representations can be defined from observable quantities in partially observable dynamical systems.

For this project, that motivates treating the framed TX as an **information-bearing observation of hidden state and intended state displacement**, rather than concluding that missing full state makes prediction impossible.

# 5. What the model receives

The final production feature encoder should be identical in training and live execution.

Conceptually:

```text
raw framed wire transaction
        ↓
same zero-allocation Rust encoder
        ↓
EncodedTxV1
        ↓
model
```

The feature groups should remain separable.

## 5.1 Structural features

Examples:

- transaction version,
- raw byte length,
- signature counts,
- static account count,
- writable/read-only/signer counts,
- instruction count,
- instruction data lengths,
- ALT counts,
- compute-unit limit,
- compute-unit price,
- instruction ordering,
- account reuse,
- writable-account sharing,
- instruction topology.

These should generalize well to unseen identities.

## 5.2 Trigger identity

The most important categorical unit is:

```text
(program_id, instruction_family)
```

The family itself should already have historical economic priors such as:

\[
P(Y=1\mid f)
\]

## 5.3 Identity features

Potentially useful but dangerous:

- program IDs,
- account IDs,
- pool IDs,
- mint IDs,
- ALT table/index identity.

These can produce strong performance through market memorization.

That may be useful in production, but it must be distinguished from genuine structural generalization.

## 5.4 Raw instruction data

Instruction bytes can encode:

- trade amount,
- price limit,
- minimum output,
- direction,
- route hints,
- flags,
- protocol-specific fields.

A raw instruction-byte branch may therefore contain strong predictive signal even before semantic decoding.

# 6. Literature: tabular models

## 6.1 Gradient-boosted trees remain mandatory baselines

Large benchmark studies have repeatedly shown that tree ensembles remain extremely strong on conventional tabular data.

Grinsztajn, Oyallon and Varoquaux (NeurIPS 2022) found tree-based models remained state of the art on their medium-sized tabular benchmark and identified useful inductive biases:

- robustness to uninformative features,
- ability to learn irregular target functions,
- suitability for axis-aligned/tabular relationships.

This strongly supports using GBDTs as a baseline for the engineered structural representation.

XGBoost is explicitly designed for scalable sparse/tabular learning and has demonstrated scaling to very large datasets.

CatBoost is particularly relevant when there are categorical identifiers because its ordered boosting/categorical machinery was designed to reduce target leakage/prediction shift associated with categorical statistics.

### Implication for this project

A serious experiment should never jump directly to a neural model.

At minimum train:

- XGBoost/LightGBM,
- CatBoost where categorical handling is useful.

If a rich deep teacher cannot significantly outperform a good GBDT on the actual economic objective, there is no reason to deploy the deep model.

---

# 7. Literature: deep tabular models

## 7.1 FT-Transformer

The *Revisiting Deep Learning Models for Tabular Data* study introduced FT-Transformer and showed that:

- strong simple MLP/ResNet baselines are competitive,
- FT-Transformer is a strong deep tabular architecture,
- there is no universally superior solution between deep tabular models and GBDTs.

FT-Transformer is valuable as a **research benchmark**, particularly when categorical embeddings and cross-feature interactions matter.

It is not attractive as the final hot-path model because attention introduces unnecessary inference cost for this latency budget.

## 7.2 TabM

TabM (ICLR 2025) is especially relevant.

The work argues that parameter-efficient ensembles of MLPs achieve a strong performance/efficiency tradeoff and reports stronger, more practical results than attention/retrieval-based tabular architectures across its evaluation.

This supports an important project conclusion:

> A sophisticated Transformer is not automatically the best neural teacher for our structured feature set.

A TabM-style model should be one of the primary neural teacher candidates.

## 7.3 DCN-V2

DCN-V2 was developed for web-scale learning/ranking systems where sparse/categorical inputs and feature interactions dominate.

Its central purpose is efficient explicit learning of feature crosses.

That matches this problem extremely well because the useful relationship may look like:

```text
instruction family
× instruction bytes
× account role
× amount structure
× program sequence
× fee configuration
```

DCN-V2 also has practical industrial evidence at web scale and was designed to remain cost-efficient.

### Implication

A **small DCN-V2-like cross component + MLP** is a particularly natural teacher/student architecture for the engineered feature path.

# 8. Raw bytes: use a small byte encoder, not a transaction Transformer initially

The raw instruction stream contains potentially useful fields but also large amounts of high-entropy identity/noise.

The first rich model should therefore not simply ingest the complete signed transaction as an unconstrained byte Transformer.

Recommended byte branch:

```text
instruction bytes
    ↓
byte embedding
    ↓
small 1D convolutions
    ↓
pooling
    ↓
fixed vector
```

Reasons:

1. Instruction data is usually short enough that local patterns are meaningful.
2. Amounts/opcodes/flags occupy fixed or semi-structured locations.
3. Convolutions are significantly cheaper than attention.
4. The structured branch already provides transaction topology.
5. The byte encoder can be removed during distillation if it offers little incremental signal.

The full raw transaction should remain available for future experiments, but the initial deep teacher should focus on **raw instruction data rather than signatures/recent blockhash bytes**.

# 9. Hierarchical family prior

This is one of the strongest problem-specific inductive biases available.

For each family \(f\), estimate a smoothed historical prior:

\[
p_f =
\frac{k_f+\alpha}
     {n_f+\alpha+\beta}
\]

where:

- \(n_f\) = eligible training examples for family \(f\),
- \(k_f\) = positives,
- \(\alpha,\beta\) = smoothing parameters.

The model then predicts a residual:

\[
\operatorname{logit}P(Y=1\mid T)
=
\operatorname{logit}(p_f)
+
r_\theta(T)
\]

Advantages:

- the model does not need to relearn the base frequency of every family,
- small families naturally shrink toward a global prior,
- learning concentrates on within-family discrimination,
- priors remain interpretable,
- the family-only baseline is explicit.

### Critical leakage rule

Family priors must be computed **from the training fold only**.

Never compute a family statistic over the complete dataset and then feed it into historical rows.

For rolling validation/deployment, use only information that would have existed before the prediction period.

# 10. Proposed teacher architecture

Recommended rich teacher:

```text
                    family prior
                         │
                         ▼
                  logit offset
                         │
STRUCTURAL FEATURES ─────┼─────► DCN / TabM-style branch
                         │
IDENTITY FEATURES ───────┼─────► categorical embeddings
                         │
INSTRUCTION BYTES ───────┼─────► small 1D CNN
                         │
                         ▼
                   fused representation
                         │
             ┌───────────┼───────────────┐
             ▼           ▼               ▼
       arb-created     value          route
          head          head           head
                         │
                  optional lifetime
```

### Suggested branch sizes

These should be tuned, but start conservatively.

Structural:

- numerical standardized/log-transformed where appropriate,
- categorical embeddings,
- DCN-V2 cross depth ~2–4,
- MLP hidden size 128–512.

Byte branch:

- byte embedding 8–32 dims,
- 2–4 Conv1D layers,
- small kernels,
- global/max pooling,
- output 32–128 dims.

No giant network is required.

The problem contains huge sample volume; capacity should be added only when validation proves it useful.

# 11. Multi-task targets

A single `created_arb` target throws away useful structure.

The teacher should learn correlated economic quantities.

## Head 1 — arb creation

Primary target:

\[
Y_{\text{created}} =
1[\text{created executable arb}]
\]

Only train this head where:

```text
label_quality == CLEAN_MARGINAL
configured_universe_complete == true
```

Do not turn unsupported/unresolved rows into negatives.

## Head 2 — value

Predict economic magnitude.

Possible formulations:

### Positive-conditional regression

For positive observations:

\[
z = \log(1+\text{net profit})
\]

Train Huber/MSE/quantile regression.

### Bucket classification

Example:

```text
no opportunity
tiny
small
medium
large
very large
```

This may be more stable initially.

The final trading decision cares about **economic value**, not classification accuracy alone.

## Head 3 — route

Do not necessarily use millions of exact route IDs immediately.

Experiment with:

- exact route ID for frequent routes,
- route family,
- venue sequence,
- token path,
- hop depth.

Evaluate **top-K route recall** because the production program only needs a small candidate set.

## Head 4 — optimal size

Useful as a hint, not as authoritative execution sizing.

Use log transformed input size / size buckets.

The on-chain program remains authoritative.

## Head 5 — lifetime

Predict:

- lifetime transactions,
- or survival thresholds such as:
  - survives >= 1 relevant update,
  - survives >= 10,
  - survives >= 100.

This may be useful for latency-aware policy later.

## Capture head

Do **not** initially share capture as the main structural target.

Capture depends strongly on competitor behavior and is more likely to drift.

Train it separately or as an optional auxiliary head with explicit temporal monitoring.

# 12. Class imbalance

Arb creation is rare globally and can still be rare within many families.

Do not optimize ordinary accuracy.

If negatives are downsampled:

- retain all positives where practical,
- sample easy negatives,
- preserve hard negatives,
- store sampling probability,
- importance-weight training/evaluation appropriately.

The validation and test distributions must retain the **real class prevalence**.

### Loss

Start with calibrated weighted binary cross entropy rather than immediately defaulting to focal loss.

Why:

- probabilities matter economically,
- BCE directly supports probability estimation,
- focal-style objectives can improve hard-example focus but can complicate calibration.

If focal loss is tested, treat it as an experiment and calibrate afterward.

---

# 13. Evaluation metrics

Because the data is imbalanced, ROC-AUC is insufficient and can be misleading.

Precision-recall analysis is more directly informative under strong class imbalance.

Report:

- PR-AUC,
- ROC-AUC only as secondary context,
- log loss,
- Brier score,
- expected calibration error,
- calibration curves,
- precision at coverage,
- recall at fixed precision,
- enrichment over family prior.

Most important production-style table:

| Selection | Coverage | Precision | Lift vs prior | Avg net opportunity | EV |
|---|---:|---:|---:|---:|---:|
| top 50% | | | | | |
| top 20% | | | | | |
| top 10% | | | | | |
| top 5% | | | | | |
| top 1% | | | | | |

The live system does not care whether the classifier's global accuracy is 99%.

It cares whether the **selected tail** contains enough economically valuable positives.

# 14. Probability calibration

Calibration is critical because the send policy will eventually evaluate expected value.

Modern neural networks are often miscalibrated.

Guo et al. showed that temperature scaling is a simple and effective calibration method in many settings.

Recommended process:

```text
train model
    ↓
untouched temporal calibration window
    ↓
fit temperature / calibration map
    ↓
freeze
    ↓
evaluate on later test window
```

Also benchmark:

- temperature scaling,
- Platt/logistic scaling,
- isotonic regression where sample size is sufficient.

Calibration must be fit only on historical data available before the test/deployment period.

Because family base rates differ, inspect calibration:

- globally,
- by major family,
- by probability bucket.

# 15. Data splitting: the most important part of the experiment

Random row splitting is unacceptable.

## 15.1 Temporal split

Minimum:

```text
TRAIN ───────────
                 VALIDATE ───
                              CALIBRATE ──
                                          TEST ─────
```

Prefer rolling walk-forward validation once more history exists.

## 15.2 Unseen-pool/account holdout

Identity features can memorize known pools.

Therefore construct an additional evaluation where selected markets/accounts appearing in test are absent from training.

Compare:

```text
structural only
structural + identity
structural + identity + raw bytes
```

If identity provides huge time-OOS gains but fails unseen-pool tests, that is market memorization.

That may still be exploitable live, but it should be understood explicitly.

## 15.3 Family support

Split results by family sample count:

```text
N < 100
100–1k
1k–10k
10k+
```

Do not make claims from tiny 1/1 or 4/62 families without uncertainty.

## 15.4 Program/version drift

When a program is upgraded or an instruction layout changes, treat it as potentially new data-generating behavior.

Version-aware families should be considered where possible.

Run these in order.

## A0 — Global prevalence

No family information.

## A1 — Family prior only

\[
P(Y\mid f)
\]

This is the minimum baseline.

## A2 — GBDT structural

Structured non-identity features only.

## A3 — GBDT structural + identity

Measures pool/program memorization value.

## A4 — TabM / DCN structured teacher

Tests nonlinear crosses and embeddings.

## A5 — Add raw instruction-byte CNN

Measures how much information exists in raw payload bytes.

## A6 — Multi-task teacher

Add profit/route/size/lifetime targets.

## A7 — Distilled student

Measures how much teacher information can survive hot-path compression.

Nothing moves forward unless it beats the simpler previous stage on the actual economic decision metrics.

# 17. Knowledge distillation

Knowledge distillation is particularly appropriate here because the best research model and the best production model have different constraints.

Hinton, Vinyals and Dean showed that knowledge from a larger/ensemble model can be transferred into a smaller deployable model.

Train the teacher with maximum useful information available from the **same causal framed-TX feature set**.

Then train a student against:

1. ground-truth labels,
2. teacher soft probabilities/logits,
3. route probability distribution,
4. optional value outputs.

Example student objective:

\[
L =
\lambda_y L_{\text{truth}}
+
\lambda_d T^2 KL(p_{\text{teacher}}^T
\Vert p_{\text{student}}^T)
+
\lambda_v L_{\text{value}}
+
\lambda_r L_{\text{route}}
\]

Distillation can smooth sparse targets and transfer cross-feature structure from a slower teacher into a tiny model.

# 18. Proposed production student

The deployed system should begin from:

\[
\operatorname{logit}(p)
=
\operatorname{logit}(p_f)
+
r_\phi(x)
\]

where \(r_\phi\) is deliberately tiny.

Candidates:

### Tiny MLP/DCN

Example starting point:

```text
input
→ cross layer(s)
→ 32/64 hidden
→ 16/32 hidden
→ heads
```

Advantages:

- dense branchless compute,
- SIMD friendly,
- straightforward C/Rust implementation,
- easy quantization,
- predictable latency.

### Oblivious tree ensemble

Example:

- 8–64 small symmetric trees.

Advantages:

- very low inference complexity,
- easy branchless/table-driven implementation,
- natural irregular decision boundaries.

Benchmark both.

There is no need to decide philosophically.

Deploy whichever gives the best:

\[
\frac{\text{economic performance gain}}
     {\text{nanoseconds}}
\]

under the actual CPU hot-path implementation.

# 19. Family-conditioned specialization

The trigger-family lookup happens before inference.

Exploit it.

Registry entry can contain:

```text
family prior
student model id
feature mask
route candidate dictionary
calibration id
```

Frequent/high-value families may get specialist models.

Long-tail families use a shared global student.

Conceptually:

```text
family lookup
     ↓
family prior
model pointer
feature mask
     ↓
only compute required features
     ↓
student inference
```

This improves both quality and latency.

Hinton et al.'s distillation paper also discusses specialist models for fine-grained classes, providing a useful conceptual precedent for global + specialist modeling.

---

# 20. Feature computation should become model-aware

The encoder currently produces a rich feature structure.

The final live model should not necessarily compute every possible field.

After model selection:

```text
trained student
    ↓
feature importance / ablation
    ↓
freeze minimal required feature mask
    ↓
production encoder fast path
```

If the final student only uses 25 features, do not calculate 150.

Preserve the richer encoder version offline, but generate a specialized hot-path projection for each student if it produces meaningful latency savings.

---

# 21. Profit-aware decision threshold

Do not select threshold from F1 score.

Eventually the decision is:

\[
EV(\text{send}\mid x)
\]

A simplified decision model:

\[
EV =
P(\text{profitable opportunity}\mid x)
\cdot E[V\mid x,Y=1]
\cdot P(\text{land}\mid x)
-
E[C_{\text{failed attempt}}\mid x]
\]

The program's on-chain economic floor reduces downside from false positives, but failed attempts are not free.

Threshold selection therefore belongs to a policy layer using:

- calibrated arb probability,
- expected opportunity value,
- route candidate quality,
- landing probability,
- fee/tip conditions,
- failed-send cost.

This is why probability calibration matters.

# 22. Recommended first training experiment

Do not begin with the full architecture.

When enough clean labels exist:

### Dataset

Filter:

```text
CLEAN_MARGINAL
configured_universe_complete
supported execution model
```

Use all accepted positive/negative economic examples.

### Inputs

V1:

- structural framed-TX features,
- program + instruction family,
- instruction prefix/raw-head features,
- optional identity hashes in a separate experiment.

### Models

Train simultaneously:

1. Family prior.
2. CatBoost/LightGBM.
3. Small MLP.
4. DCN-V2-style network.
5. TabM.

No byte CNN initially unless the V1 encoder already exposes a clean bounded representation.

### Determine whether signal exists

For each model measure:

```text
family baseline
top 20%
top 10%
top 5%
top 1%
```

If an 18% family prior turns into:

```text
top 10% = 45–60%+
```

the premise is strongly supported.

Only then add raw byte branches and larger teachers.

# 23. When to add the byte teacher

Add a raw instruction-byte encoder only after the structured model establishes signal.

Test:

\[
\Delta =
\text{teacher(structured+bytes)}
-
\text{teacher(structured)}
\]

If \(\Delta\) is small, do not burden the production architecture.

If it is large, distill its information into the student.

This experimental discipline prevents the project becoming "deep learning because raw bytes look complicated."

---

# 24. What not to use as the production model

## Full Transformer over raw transaction bytes

Not recommended initially because:

- unnecessary attention cost,
- signatures/blockhash/account identities add noise,
- transaction structure is already known explicitly,
- hot-path latency requirement is extreme.

Use only as a research challenger if evidence later warrants it.

## TabPFN

Interesting research direction in tabular foundation modeling, but not suitable for this enormous dataset and sub-microsecond deployment objective.

## Giant boosted ensemble

May perform extremely well offline but likely violates the live latency budget if hundreds/thousands of trees are required.

Useful teacher/baseline, not automatically the production model.

## End-to-end model using post-state/runtime information

Invalid due to leakage.

# 25. Stationarity diagnostics

Explicitly monitor whether the deterministic mechanical target behaves as expected.

For every major family calculate over rolling time buckets:

```text
arb creation rate
profit distribution
route distribution
model precision
model calibration
```

Separately monitor:

```text
capture rate
capture lifetime
```

Expected desirable pattern:

```text
creation mechanics relatively stable
competition metrics drift faster
```

If creation rates themselves shift sharply, investigate:

- program upgrade,
- liquidity-regime change,
- new pool population,
- token-regime change,
- label universe expansion,
- feature/data bug.

# 26. Model refresh strategy

Because the structural model is expected to be more stationary than the competition model:

### Structural arb model

Retrain when:

- enough new labeled data exists,
- important family distribution changes,
- protocol versions change,
- OOS calibration/performance degrades.

### Capture/competition model

Refresh more frequently.

Possible architecture:

```text
slow-changing creation model
          ×
fast-changing competition/landing model
          ↓
      live send EV
```

# 27. Compute and training strategy

The eventual dataset may contain tens/hundreds of millions of labeled economic rows and much larger raw transaction corpora.

Suggested workflow:

### Development

- train on smaller temporal slices locally,
- rapidly test feature/model hypotheses.

### Final teacher

Rent GPU(s) for:

- TabM/DCN/byte-CNN teacher,
- multi-task training,
- distillation generation.

### Student

Train/export tiny CPU model.

The production searcher does not require a GPU.

The expensive training machine can be rented, models exported, and the instance terminated.

---

# 28. Success criteria

The modeling thesis is supported if all of the following occur:

1. Family priors show repeatable differences.
2. Individual framed-TX features significantly enrich positive probability within families.
3. Enrichment survives strict temporal OOS tests.
4. A useful portion survives unseen-pool tests.
5. Probabilities can be calibrated.
6. Top-K route recall is high enough to keep on-chain candidate evaluation small.
7. Distilled student retains most of teacher quality.
8. Student meets the measured latency budget.
9. Expected send EV improves over family-only triggering.

The key comparison is never:

> Does ML have high accuracy?

It is:

> Does ML improve economic selection enough, at sufficiently low latency, to beat family-only triggering?

# 29. Final recommendation

## Research teacher

Use a **hierarchical multi-task hybrid teacher**:

```text
smoothed family prior
        +
DCN-V2 / TabM-style structured branch
        +
categorical identity embeddings
        +
small instruction-byte CNN
        ↓
arb probability
economic value
route/top-K
size
survivability
```

Not every branch needs to survive experimentation; ablate them.

## Production student

Use:

```text
family prior
+
tiny family-conditioned residual model
```

Benchmark:

- tiny DCN/MLP,
- small oblivious-tree ensemble.

Distill the rich teacher into the best latency/quality student.

## Training

- strict temporal splits,
- training-fold-only family priors,
- real-prevalence validation,
- explicit unknown/unsupported filtering,
- multi-task teacher,
- probability calibration,
- distillation,
- pool/generalization holdouts.

## Selection metric

Optimize:

```text
precision / economic value at deployable coverage
+
calibration
+
top-K route recall
+
latency
```

not raw accuracy or ROC-AUC.

This architecture best matches the unusual structure of the problem:

**a deterministic blockchain transition, partially hidden state, a very large but structured historical corpus, and an extremely constrained live inference budget.**

# 31. Immediate experimental checklist

Once the first solid labeled dataset exists:

- [ ] Build family-only prior baseline.
- [ ] Lock strict temporal train/validation/calibration/test windows.
- [ ] Ensure unsupported/unresolved labels are excluded rather than made negative.
- [ ] Train LightGBM/XGBoost baseline.
- [ ] Train CatBoost categorical baseline.
- [ ] Train small MLP.
- [ ] Train DCN-V2-style model.
- [ ] Train TabM teacher.
- [ ] Compare family enrichment curves.
- [ ] Add identity features and repeat.
- [ ] Run unseen-pool holdout.
- [ ] Add raw instruction-byte CNN only if justified.
- [ ] Train multi-task teacher.
- [ ] Calibrate probabilities.
- [ ] Distill teacher to tiny student.
- [ ] Benchmark student in the exact Rust/C live inference path.
- [ ] Optimize send threshold by economic EV, not classification score.
